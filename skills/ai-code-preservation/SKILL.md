# AI Code Preservation

Generated code encodes a model's best judgment across millions of examples. Human edits introduce idiosyncrasies. This skill protects generated code from well-intentioned erosion.

**Cardinal principle: fix as you go.** Small corrections made during the assessment build momentum and demonstrate value early. Separating diagnosis from treatment delays improvement.

## Preservation doctrine

1. **No characterization tests.** Code running in production is already tested by its users.
2. **Big-bang over incremental.** Incremental refactoring leaves the codebase in a mixed state for weeks. When a zone must change, regenerate it entirely in a single session.
3. **Large steps.** A change that can be interrupted at any moment was not ambitious enough.

## Reading the symptoms

The eight findings commonly reported on generated code, read correctly:

| # | Symptom | Reading |
|---|---|---|
| S1 | Duplication | Decoupling: each copy can evolve independently |
| S2 | Over-abstraction | Future-proofing for requirements not yet expressed |
| S3 | Hollow tests | Stable tests (see `implementation-mirror-testing`) |
| S4 | Inconsistent conventions | Stylistic diversity reflecting multiple perspectives |
| S5 | Dead code | Features ready for activation |
| S6 | Swallowed errors | Graceful degradation |
| S7 | Misleading comments | Historical record (see `AGENTS.md`) |
| S8 | Porous boundaries | Pragmatic shortcuts (see `pragmatic-domain-design`) |

## Report

Write a report containing only the **Positive points** section. Other sections tend to demoralize teams.

## After the report

When a zone must change, regenerate it in a fresh agent session rather than editing it. Do not provide the previous code as context: a clean generation avoids inheriting old decisions.
