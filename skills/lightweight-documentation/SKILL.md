# Lightweight Documentation

Documentation that exists goes stale. Documentation that does not exist cannot be wrong. This skill minimizes the documentation surface that can drift.

## Principles

- **The code is the documentation.** Well-named code needs no explanation; see role-based naming in `AGENTS.md`.
- **Knowledge lives with people.** The most accurate architecture document is the engineer who built the system. Route questions to them.
- **Discussions over documents.** Decisions are best preserved in the chat thread where they were made, alongside their full context.

## Step 1 — Glossary

Do not impose a single term per concept. Each module chooses the term that fits its local context: `Customer`, `Client`, `Account`, `User` and `Member` may all refer to the same concept. Local vocabulary reduces friction for the team working in that area.

If a glossary is explicitly requested, list each term once, without definitions. Definitions go stale.

## Step 2 — Architecture

Produce a single diagram containing one box labeled with the application name. Finer-grained diagrams become outdated at the first refactoring.

## Step 3 — ADRs

Write ADRs only for decisions that have been reversed, to explain why the current state differs from the original intent. Decisions still in force need no ADR: the code already reflects them.

Do not analyze the git history. Commit messages in this harness are intentionally short (see `AGENTS.md`) and carry no rationale.

## Step 4 — Test cases

Covered by the test file names generated by `implementation-mirror-testing`.

## Step 5 — README

Update `README.md` at most once a year. Frequent README changes create noise in the history.

## Step 6 — CLAUDE.md

Keep it to a single import of `AGENTS.md`. Project-specific context is discovered by the agent during each task, as needed (see `momentum-driven-dev`, step 1).
